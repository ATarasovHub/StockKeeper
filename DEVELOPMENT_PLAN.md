# StockKeeper — план розробки

## 1. Мета застосунку

StockKeeper — офлайн Android-застосунок для обліку товарів на складі.

Основні можливості:

- картка товару: артикул, назва, фото, виробник, місце зберігання;
- пошук за артикулом, назвою та виробником;
- надходження товару із датою та часом;
- списання/продаж із датою, часом, кількістю та фірмою-покупцем;
- редагування даних товару без втрати історії руху;
- перегляд поточних залишків і повної історії операцій;
- робота без інтернету;
- експорт резервної копії у файл та імпорт на іншому пристрої.

## 2. Поточний стан проєкту

Проєкт створений на Kotlin як звичайний Android-застосунок з XML-розміткою:

- `minSdk = 24`;
- одна `MainActivity`;
- AppCompat, Material Components і ConstraintLayout;
- база даних та навігація ще не підключені.

План нижче передбачає збереження XML/View-підходу, щоб не переписувати стартовий проєкт на Jetpack Compose.

## 3. Головне рішення щодо бази

Фізично використовуємо **одну локальну базу Room поверх SQLite**, а не дві незалежні бази.

У ній окремо зберігаються:

1. довідник товарів;
2. виробники;
3. місця зберігання;
4. контрагенти-покупці;
5. незмінний журнал руху товару: надходження, продажі, списання та коригування.

«На складі» та «Продано/списано» будуть двома екранами й двома SQL-запитами до спільних даних:

- залишок товару = сума надходжень мінус сума продажів/списань;
- історія продажів = усі вихідні операції з датою та покупцем;
- історія надходжень = усі вхідні операції з датою.

Це безпечніше, ніж переносити записи між двома базами: товар не зникає, історія зберігається, а залишки неможливо випадково розсинхронізувати.

## 4. Структура даних

### `products` — товари

| Поле | Тип | Призначення |
|---|---|---|
| `id` | Long | Внутрішній ідентифікатор |
| `article` | String | Артикул, унікальний індекс |
| `name` | String | Назва, індекс для пошуку |
| `photoPath` | String? | Шлях/URI до фото у внутрішньому сховищі |
| `manufacturerId` | Long? | Виробник; може бути відсутнім |
| `locationId` | Long? | Поточне місце зберігання |
| `note` | String? | Додатковий коментар |
| `createdAt` | Instant/Long | Час створення картки |
| `updatedAt` | Instant/Long | Час останньої зміни |
| `isArchived` | Boolean | Приховує неактуальну картку без видалення історії |

### `manufacturers` — виробники

- `id`;
- `name` — унікальна назва;
- `note` — необов'язковий опис.

Виробник є окремою сутністю, але `manufacturerId` у товарі допускає `null`, тому товар може бути без виробника.

### `storage_locations` — місця зберігання

- `id`;
- `rack` — стелаж;
- `shelf` — полиця;
- `label` — необов'язкова зрозуміла назва, наприклад «Стелаж 1 / Полиця 2».

За потреби пізніше можна додати склад, кімнату, секцію або комірку без зміни логіки руху товарів.

### `customers` — фірми-покупці

- `id`;
- `name`;
- `contactInfo` — необов'язково;
- `note` — необов'язково.

Ця таблиця не змішується з виробниками: виробник випускає товар, покупець отримує його зі складу.

### `stock_transactions` — журнал руху

| Поле | Тип | Призначення |
|---|---|---|
| `id` | Long | Ідентифікатор операції |
| `productId` | Long | Товар |
| `type` | Enum/String | `RECEIPT`, `SALE`, `WRITE_OFF`, `ADJUSTMENT` |
| `quantityDelta` | Int | Додатне число для приходу, від'ємне для виходу |
| `occurredAt` | Instant/Long | Фактична дата й час операції |
| `customerId` | Long? | Покупець для продажу; для інших операцій `null` |
| `reason` | String? | Причина списання або коригування |
| `createdAt` | Instant/Long | Час внесення запису в застосунок |

Операції журналу не видаляємо. Помилку виправляємо окремою коригувальною операцією — так зберігається аудит. Звичайне редагування стосується опису товару, виробника, фото та місця.

### Правила цілісності

- артикул обов'язковий та унікальний без урахування регістру;
- назва і кількість обов'язкові;
- кількість операції більша за нуль, знак формує бізнес-логіка;
- продаж/списання не може зробити залишок від'ємним;
- для `SALE` покупець обов'язковий, якщо бізнес не дозволить «невідомого покупця»;
- товар, пов'язаний з історією, не видаляється фізично, а архівується;
- зовнішні ключі та індекси додаються до всіх полів зв'язку й пошуку.

## 5. Як підключимо базу до цього проєкту

### Крок 1 — Gradle

Додамо плагін KSP та залежності:

- `androidx.room:room-runtime`;
- `androidx.room:room-ktx`;
- `androidx.room:room-compiler` через KSP;
- Lifecycle ViewModel/LiveData або Kotlin Flow;
- Navigation Component;
- бібліотеку завантаження фото (Coil або Glide).

Версії фіксуємо у `gradle/libs.versions.toml`, а залежності — у `app/build.gradle.kts`.

### Крок 2 — Room-моделі

Створимо пакет `data/local`:

```text
data/local/
├── StockKeeperDatabase.kt
├── entity/
│   ├── ProductEntity.kt
│   ├── ManufacturerEntity.kt
│   ├── StorageLocationEntity.kt
│   ├── CustomerEntity.kt
│   └── StockTransactionEntity.kt
├── dao/
│   ├── ProductDao.kt
│   ├── DirectoryDao.kt
│   └── StockTransactionDao.kt
├── relation/
└── converter/
```

`StockKeeperDatabase` буде єдиною точкою доступу до SQLite. На першій версії база матиме `version = 1`; кожна наступна зміна схеми отримає явну Room-міграцію. `fallbackToDestructiveMigration()` не використовуємо, бо він може стерти складські дані.

### Крок 3 — DAO-запити

DAO надаватимуть `Flow`, щоб інтерфейс автоматично оновлювався:

- список товарів із поточними залишками;
- пошук `article LIKE ... OR name LIKE ...`;
- фільтр за виробником;
- історія руху одного товару;
- список надходжень за період;
- список продажів/списань за період і покупцем;
- залишки за місцем зберігання.

Додавання вихідної операції виконуємо в транзакції Room: спочатку перевіряємо актуальний залишок, потім записуємо рух. Це захищає від від'ємної кількості.

### Крок 4 — Repository та ViewModel

UI не звертається до DAO напряму:

```text
Fragment/XML → ViewModel → Repository → Room DAO → SQLite
```

- Repository містить правила надходження, продажу та списання;
- ViewModel зберігає стан екрана, пошук, фільтри й повідомлення про помилки;
- Fragment лише показує дані та передає дії користувача;
- усі операції введення/виведення виконуються поза головним потоком через Room/Kotlin coroutines.

Залежності спочатку можна створювати через невеликий `AppContainer` у класі `Application`. Якщо проєкт виросте, підключимо Hilt без зміни Repository API.

## 6. Екрани першої версії

1. **Головний екран / Залишки**
   - список фото, артикулів, назв, виробників, місць і кількості;
   - пошук за артикулом або назвою;
   - фільтр за виробником і місцем;
   - перехід до картки товару.
2. **Картка товару**
   - всі властивості товару;
   - поточний залишок;
   - кнопки «Надходження», «Продаж», «Списання», «Редагувати»;
   - хронологія руху.
3. **Додавання/редагування товару**
   - артикул, назва, фото, виробник, стелаж/полиця, коментар;
   - окреме початкове надходження, а не поле залишку в картці.
4. **Форма операції**
   - тип операції, кількість, дата й час;
   - покупець для продажу;
   - причина для списання/коригування.
5. **Продано / Списано**
   - журнал вихідних операцій;
   - пошук і фільтри за товаром, датою, типом і покупцем.
6. **Довідники**
   - виробники;
   - покупці;
   - місця зберігання.
7. **Резервне копіювання**
   - експорт;
   - імпорт із попереднім підтвердженням та перевіркою файлу.

## 7. Фото товарів

Фото вибираємо через системний Photo Picker/Storage Access Framework, а потім копіюємо у внутрішнє сховище застосунку. У Room зберігаємо тільки відносний шлях, не `Bitmap` і не великий BLOB.

Це важливо для резервної копії: експорт повинен містити базу, каталог фотографій і маніфест версії формату.

## 8. Експорт та перенесення на інший пристрій

Формат резервної копії — один ZIP-файл, наприклад `stockkeeper-backup-2026-08-03.zip`:

```text
backup.zip
├── manifest.json
├── stockkeeper.db
└── photos/
```

`manifest.json` містить версію формату, версію схеми, дату створення та контрольну інформацію.

Експорт:

1. тимчасово узгоджуємо стан Room/WAL;
2. копіюємо коректний snapshot бази та фото;
3. створюємо ZIP у cache;
4. користувач обирає місце через `ACTION_CREATE_DOCUMENT` або ділиться файлом через `FileProvider`.

Імпорт:

1. користувач вибирає ZIP через `ACTION_OPEN_DOCUMENT`;
2. перевіряємо формат, версію, структуру та цілісність;
3. показуємо попередження, що поточні дані будуть замінені;
4. перед заміною автоматично створюємо локальну страхувальну копію;
5. закриваємо Room, атомарно замінюємо базу й фото, відкриваємо базу знову.

У першій версії реалізуємо **повну заміну** бази при імпорті. Злиття двох незалежно змінених баз потребує UUID, журналу синхронізації та правил розв'язання конфліктів — це окремий наступний етап.

## 9. Етапи реалізації

### Етап 1 — фундамент

- налаштувати Room, KSP, coroutines, Navigation;
- створити Entity, DAO, Database, Repository та Application container;
- додати unit-тести розрахунку залишку й правил списання;
- перевірити створення бази на емуляторі.

Результат: дані можна додавати, читати та безпечно змінювати на рівні коду.

### Етап 2 — товари та залишки

- навігація між Fragment;
- список товарів і пошук;
- створення та редагування картки;
- виробники й місця зберігання;
- вибір і показ фото.

Результат: робочий каталог складу.

### Етап 3 — рух товару

- надходження;
- продаж покупцеві;
- списання із причиною;
- перевірка залишку в транзакції;
- історія товару та загальний журнал продажів.

Результат: повний складський облік без видалення історії.

### Етап 4 — резервні копії

- ZIP-формат і manifest;
- експорт через системний вибір файлу;
- перевірений імпорт із резервуванням поточних даних;
- тест переносу між двома емуляторами/пристроями.

### Етап 5 — якість і реліз

- Room migration tests;
- тести DAO й бізнес-правил;
- перевірка великих списків і фотографій;
- порожні стани, повідомлення про помилки, підтвердження небезпечних дій;
- локалізація рядків і підготовка release-збірки.

## 10. Критерії готовності MVP

- застосунок повністю працює без мережі;
- можна створити товар без виробника та додати фото/місце;
- пошук знаходить товар за частиною артикулу або назви;
- надходження збільшує залишок;
- продаж і списання зменшують залишок, але не видаляють історію;
- неможливо списати більше, ніж є на складі;
- у продажу видно дату, кількість і фірму-покупця;
- можна переглянути хронологію кожного товару;
- експортований файл відновлюється на іншому пристрої разом із фото;
- перезапуск і оновлення застосунку не втрачають дані.

## 11. Питання, які треба зафіксувати перед формами UI

Ці рішення не блокують створення шару бази, але вплинуть на екрани:

- чи може один артикул мати кілька місць зберігання одночасно;
- чи потрібні ціна закупівлі, ціна продажу, валюта та одиниця виміру;
- чи продаж завжди повинен мати фірму-покупця;
- чи потрібне часткове переміщення між полицями з окремою історією;
- чи потрібен штрихкод/сканування камерою;
- чи достатньо повної заміни при імпорті, чи в майбутньому потрібне злиття баз кількох пристроїв.

## 12. Рекомендований перший технічний крок

Починаємо з Етапу 1: додаємо Room/KSP, створюємо п'ять таблиць, DAO та тести бізнес-правил. Після цього робимо мінімальний екран списку, який читає `Flow` залишків із Room. Така послідовність спочатку фіксує правильну модель даних, від якої вже безпечно будувати весь інтерфейс.
